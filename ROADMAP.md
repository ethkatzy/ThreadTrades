# ThreadTrades — Roadmap / Deferred Decisions

Decisions intentionally punted past initial scaffolding. Each one is designed to be
swappable later without a rewrite (see the `storage/` interface pattern and Docker Compose
setup in the initial scaffold) — revisit when the trigger condition hits, not on a fixed date.

## 1. Object / file storage backend

**Decided (2026-08-24): Cloudflare R2.** Local disk storage sits behind a
`StorageService` interface (`backend/.../storage/`), so this was a config + one new
implementation class (`R2StorageService`), not a rewrite. `app.storage.provider`
(`STORAGE_PROVIDER` env var) selects between `local` (default, dev-only) and `r2` —
see `.env.example` for the full set of `R2_*` vars it needs. This was picked because
the goal isn't a real product (see #2) — R2's free tier should stay $0 indefinitely
at portfolio-project traffic, unlike S3 (12-month free tier, then egress fees).

| Option | Pros | Cons |
|---|---|---|
| **Cloudflare R2** | S3-compatible API (same SDK/code as S3); **no egress fees**, which matters for an image-heavy app people browse a lot; generous free tier | Smaller ecosystem than AWS; fewer tutorials/Stack Overflow answers if something goes wrong |
| **AWS S3** | Most standard/ubiquitous choice; best tooling and docs; pairs naturally if you ever deploy on AWS (EC2/ECS/Lambda) | Egress fees can add up for an image-browsing app; more complex IAM/permissions model to get right |
| **Self-hosted MinIO (Docker)** | Zero external account/cost; runs alongside Postgres in the same `docker-compose.yml`; fully S3-API-compatible so code doesn't change if you migrate to real S3/R2 later | You own the ops (backups, disk space, uptime); doesn't solve the "reachable from the internet" problem on its own — still needs a real host with persistent storage |
| **Local disk (current default)** | Zero setup, zero cost, works today | Not portable, doesn't survive redeploys/scaling, only viable for local development |

**Leaning:** R2 is the natural next step when you leave local disk — cheapest at this
app's likely traffic pattern (lots of image reads, few writes) and a drop-in S3-compatible
swap given the interface is already abstracted.

## 2. Deployment target

**Decided (2026-08-24): Render (web services) + Neon or Supabase (Postgres), not
Render's own Postgres.** Goal is a live demo for a GitHub portfolio, not a real
product — priorities are $$0 ongoing cost and zero ops attention, not scale. Fly.io
dropped its free tier entirely in 2026 (real billing floor once a Postgres instance
is added, roughly $8-12/mo); Render's web services stay free indefinitely (they
spin down after 15 min idle, ~1 min cold start on the next request — a non-issue
for occasional recruiter visits) but its free Postgres **expires after 30 days**,
so the database goes to Neon or Supabase instead, both of which have a free tier
with no expiry. See `render.yaml` for the blueprint and `backend/Dockerfile` /
`frontend/Dockerfile` for the production images (the `Dockerfile.dev` variants run
dev servers against a bind-mounted source tree and are Compose/local-only).

## 3. Notes from implementation (discovered along the way)

Gotchas and small trade-offs hit while building auth, upload, and the dashboard.
Most were fixed on the spot and are recorded so the same shape of bug doesn't cost
time twice; a handful are still live trade-offs. The **Worth doing? (0–10)** column
is my read on how much value there'd be in acting on a row *at some point* — not
urgency, and not a status field. Most rows below score low because they're already
fixed and there's nothing left to do; a 0 there just means "no further action has
any value," not "this was unimportant." A handful of genuinely open trade-offs
score higher because doing something about them would be a real, if non-urgent,
improvement.

### Security

| Problem | Affects | Possible change | Worth doing? (0–10) |
|---|---|---|---|
| ~~JWT lives in browser `localStorage`, not an httpOnly cookie~~ — **Fixed (2026-08-25).** The backend now sets the JWT as an httpOnly `tt_session` cookie (`SessionCookieService`) on login/register instead of returning it in the JSON body; the frontend dropped all token plumbing and just uses `credentials: "include"` on every fetch (`client.ts`). | Session/auth security for every logged-in user. | Done — see the implementation-gotcha rows below for what it actually took. | **0/10.** Done. Cookie flags are configurable (`COOKIE_SECURE`/`COOKIE_SAME_SITE`, `.env.example`) — `false`/`Lax` locally, `true`/`None` on Render. |
| Moving auth to a cookie reopens CSRF (a cookie rides along on cross-site requests automatically; a bearer header never did). | Every mutating (`POST`/`PATCH`/`DELETE`) endpoint, especially the multipart upload/profile-picture ones — `multipart/form-data` is a CORS-preflight-exempt "simple" content type, so without CSRF protection a hidden cross-site form could trigger those even though JSON endpoints happen to be preflight-guarded already. | Spring Security 7 ships a purpose-built `.csrf(csrf -> csrf.spa())` preset for exactly this (SPA + cookie auth): a JS-readable `XSRF-TOKEN` cookie + `X-XSRF-TOKEN` header double-submit check. | **0/10.** Done — wired into `SecurityConfig`, frontend reads the cookie and echoes the header in `client.ts` for every non-GET request. |
| **`csrf.spa()` alone never actually issues the `XSRF-TOKEN` cookie on a pure REST API.** Spring Security's cookie-backed CSRF token is generated lazily — the cookie is only written once something calls `CsrfToken#getToken()`, which normally happens when a server-rendered form reads `${_csrf.token}`. A JSON API never does that, so nothing would trigger it. | Any cookie-based CSRF setup on a backend with no server-rendered views. | Add a small `OncePerRequestFilter` (`CsrfCookieFilter`) that unconditionally calls `.getToken()` on every request, forcing the write. This is Spring Security's own documented fix for SPA clients, not a local workaround. | **0/10.** Done (`CsrfCookieFilter`, `addFilterAfter(..., BasicAuthenticationFilter.class)` — that anchor class doesn't need to be otherwise enabled; Spring Security pre-registers a fixed order for all known filter classes regardless). |
| **A CSRF failure surfaces as `401 Unauthorized`, not `403 Forbidden`.** `CsrfFilter` runs earlier in the chain than this app's own `JwtAuthenticationFilter`, so when CSRF validation fails the `SecurityContext` is still anonymous — Spring Security routes an `AccessDeniedException` with no authenticated principal to the `AuthenticationEntryPoint` instead of the `AccessDeniedHandler`. | Debugging any "why am I getting 401 on a request that should just need a fresh cookie" symptom. | Could give `JsonAuthenticationEntryPoint` more context to distinguish "no session" from "CSRF rejected," but the mapping itself is standard Spring Security behavior, not a bug. | **1/10.** Cost real time once in `WebSocketMessagingTest` (looked like a broken session cookie, was actually a missing `X-XSRF-TOKEN`), so it's worth remembering — but a nicer error message for a case this rare isn't worth the code. |
| STOMP CONNECT frames carry no cookie of their own (they're not HTTP requests) — the old design carried the JWT as a STOMP `Authorization` header instead, which no longer exists once the token lives in an httpOnly cookie the client can't read. | WebSocket auth (`StompAuthChannelInterceptor`). | A `HandshakeInterceptor` (`SessionCookieHandshakeInterceptor`) reads the session cookie off the raw WS handshake request (browsers attach cookies to that handshake automatically, same as any other request) and stashes the parsed user in the WebSocket session's `attributes`, which Spring copies onto every STOMP frame's `accessor.getSessionAttributes()` in that session. | **0/10.** Done. Cross-site WS hijacking is separately guarded by `setAllowedOrigins(...)` on the STOMP endpoint (checked against the `Origin` header, which — unlike cookies — a page can't spoof), so this didn't need its own CSRF-equivalent. |
| **`TestRestTemplate` has no cookie jar** (unlike a browser, it won't remember or replay `Set-Cookie` values between requests). | `WebSocketMessagingTest`, the one test class that can't use MockMvc's `SecurityMockMvcRequestPostProcessors.csrf()` shortcut (it drives real sockets over a random port). | Manually extract both the `tt_session` and `XSRF-TOKEN` cookie values from each response and replay them (`Cookie` header for both + `X-XSRF-TOKEN` header) on every subsequent call — see `WebSocketMessagingTest.Session`/`authHeaders()`. | **0/10.** Done. A related trap: a single response can carry **two** `Set-Cookie` headers for the same cookie name (e.g. register returns a clearing `XSRF-TOKEN=;` from `CsrfFilter`'s exemption handling for that path, immediately followed by a fresh one from `CsrfCookieFilter` forcing eager generation) — a real browser's cookie jar just nets these out to the last value, so the test's extraction helper has to explicitly skip empty values and take the last match rather than the first. |
| Render's two services (`*.onrender.com`) are on the Public Suffix List, so they're cross-**site**, not just cross-origin — `SameSite=Lax` would silently stop the browser from ever attaching the cookie to the frontend's fetch calls to the backend at all (Lax only allows cross-site *top-level navigations*, not subresource fetches), breaking auth entirely, not just reopening CSRF. | Production cookie behavior specifically (local dev has both services under `localhost`, which **is** same-site regardless of port, so this doesn't reproduce there). | `SameSite=None` (requires `Secure`) in production; `Lax` is fine locally. | **0/10.** Done — `COOKIE_SAME_SITE=None` set in `render.yaml` for the backend service, default stays `Lax` locally. |
| **The `COOKIE_SECURE`/`COOKIE_SAME_SITE` fix above only covered `tt_session`.** `csrf.spa()`'s default `CookieCsrfTokenRepository` writes the `XSRF-TOKEN` cookie with its own hardcoded defaults, independent of `SessionCookieService` — on Render that meant `XSRF-TOKEN` went out with no `SameSite` attribute (browser default `Lax`) despite the app being configured `None`/`Secure` everywhere else. First-load and login/register still worked (both are CSRF-exempt), but every other mutating request 401'd once the browser silently dropped the cookie, reproducing the `401`-not-`403` symptom from the row above **in production only** (local dev is same-site, so this cookie is never blocked there either) — this is the "why does login work but uploading doesn't" bug hit 2026-08-25 testing the live Render deploy. | Every non-`/api/auth/register`/`/api/auth/login` mutating endpoint, production only. | `CookieCsrfTokenRepository` (Spring Security 6.4+) exposes `setCookieCustomizer(Consumer<ResponseCookieBuilder>)` specifically for this — built a `CookieCsrfTokenRepository` bean customized with the same `app.cookie.secure`/`app.cookie.same-site` values as `SessionCookieService` and wired it into `.spa().csrfTokenRepository(...)` in `SecurityConfig`. | **0/10.** Done. |
| **Even with `SameSite=None` correctly set, the frontend can never read `XSRF-TOKEN` on Render — the SameSite fix above was necessary but not sufficient.** `document.cookie` is scoped to the page's own origin; it can never return a cookie set by a *different* origin no matter what cookie flags say. `getCsrfToken()` (`csrf.ts`) runs on `threadtrades-frontend.onrender.com`, but `XSRF-TOKEN` is set by `threadtrades-backend.onrender.com` — a different site. So it always returned `null` in production, `X-XSRF-TOKEN` was never sent, and every CSRF-protected mutating request (logout, uploads, ...) kept 401ing even after the SameSite fix deployed and was verified correct via curl. Cost real time 2026-08-25 because the symptom (401 on logout/upload, login/register fine) looked identical to the SameSite bug it followed. | Every non-`/api/auth/register`/`/api/auth/login` mutating endpoint, production only — confirmed with `document.cookie` returning `""` on the live frontend page. | The double-submit CSRF pattern fundamentally requires frontend JS to read the cookie, which requires frontend and backend to be the *same site* — no cookie flag combination substitutes for that. Added a Next.js `rewrites()` proxy (`next.config.ts`) so the browser only ever talks to its own origin; `/api/**` is forwarded server-side to the real backend (`BACKEND_INTERNAL_URL`), and `client.ts` now fetches relative paths instead of an absolute backend URL. Every `Set-Cookie` the backend sends is then indistinguishable, to the browser, from one set by the frontend itself. | **0/10.** Done. The alternative (custom domain with frontend/backend as sibling subdomains, so cookies can use an explicit shared `Domain`) was considered and rejected — it needs a domain the project doesn't have, where the proxy needs nothing beyond `render.yaml`/`next.config.ts` changes. |
| **`next.config.ts`'s `rewrites()` destination is resolved once at `next build` time, not read fresh at `next start`.** The resolved URL gets baked into `.next/routes-manifest.json` at build time; changing the env var it reads and just restarting the container (no rebuild) silently keeps proxying to the old value forever. This is easy to miss because it's *not* a `NEXT_PUBLIC_*` var (those are known/expected to be build-time-baked, per the existing `NEXT_PUBLIC_API_URL` gotcha in `frontend/Dockerfile`) — it's a plain server-side var, which everywhere else in this codebase (`COOKIE_SECURE`, `STORAGE_PROVIDER`, ...) is read fresh at container start. | `BACKEND_INTERNAL_URL` specifically (the proxy target for the row above) — any future server-side var read inside `next.config.ts` itself (as opposed to inside route/page code) would have the same issue. | Verified by building twice locally with different `BACKEND_INTERNAL_URL` values and grepping `.next/routes-manifest.json` for which one won. Declared `ARG BACKEND_INTERNAL_URL` in `frontend/Dockerfile` right alongside the `NEXT_PUBLIC_*` ARGs so Render forwards it as a build arg the same way, even though it isn't one. | **0/10.** Done. |
| Every `/admin/*` page had its own `if (!token) return` guard on each data-fetching effect, left over from when `token` (not `user`) was the thing `useAuth()` exposed — but `AdminLayout` already blocks rendering `children` at all until `user` is a confirmed `ADMIN` (see its own comment: "the one place the admin role check happens"). | Code cleanliness only, once `token` stopped existing on the auth context. | Drop the redundant per-page guards instead of swapping them to check `user`. | **0/10.** Done — simplified while migrating off `token`, not a separate task. |

### Backend / Hibernate / JPA

| Problem | Affects | Possible change | Worth doing? (0–10) |
|---|---|---|---|
| Spring Boot 4 runs Jackson 3 internally, but `jjwt-jackson` pulls in Jackson 2 transitively — autowiring `com.fasterxml.jackson...ObjectMapper` in tests isn't reliable. | Test code only. | None — already worked around with raw JSON + `JsonPath`. | **0/10.** Resolved convention; only resurfaces if `jjwt-jackson` ever ships a Jackson-3-native build, which isn't something to act on preemptively. |
| Spring Boot 4 moved `@AutoConfigureMockMvc` to `org.springframework.boot.webmvc.test.autoconfigure`. | Import paths in new test classes. | None. | **0/10.** Just a fact to remember. |
| `@DynamicPropertySource` suppliers re-run on every property lookup, not once — non-idempotent suppliers (e.g. with `UUID.randomUUID()`) hand different beans different values. | Test config correctness. | None — already worked around with a `static final`. | **0/10.** Resolved convention. |
| Hibernate's `ddl-auto=validate` is strict about exact column type — a Java `int` needs SQL `INTEGER`, not just anything that fits (e.g. `SMALLINT` failed). | Any migration backing an `int`/`Integer` field. | None — already fixed. | **0/10.** Just a rule to remember when writing the next migration. |
| Existing Response-record `from(...)` factories default to package-private, blocking reuse from a new cross-cutting package (hit when the admin endpoints wanted to reuse `MessageResponse`/`ReviewResponse`). | Cross-package DTO reuse. | None — already widened to `public` where needed. | **0/10.** Just check visibility first next time a DTO is reused from a new package. |
| `item_match`'s FKs to `clothing_item` are `ON DELETE CASCADE`, so a real `DELETE` on an item would silently cascade away its match/swap/message history. | Any hard-delete admin action on an entity with inbound FKs. | None — status flags (`ItemStatus.REMOVED`) already used instead, consistent with `Swap`/`Review`. | **0/10.** This is the correct design already in place, not a defect. |
| Enum-like columns are `VARCHAR` + `CHECK`, not a native Postgres enum (deliberate, per `V1`'s header comment) — adding a value means `DROP`/`ADD CONSTRAINT` and getting Postgres's auto-generated constraint name right. | Any future new enum value on an existing column. | None — working as designed. | **0/10.** Deliberate trade-off; just remember the migration mechanics. |
